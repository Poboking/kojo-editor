# 口上编辑器（kojo-editor）调研文档

- **版本**：v1.0
- **日期**：2026-10-09
- **性质**：项目立项前的调研汇总。姊妹篇《ARCHITECTURE.md》（架构设计）承接本文结论。
- **调研方法**：eraTW 4.980 全量目录实测 + 引擎/口上分发器源码精读（16 篇逆向文档）+ 游戏自带作者教程/模板/补丁生态文本分析。

---

## 1. 问题陈述

eraTW 口上是 Emuera/ERB 生态中体量最大、结构最规整的剧本子系统，但作者侧工具链停留在 **2000 年代水平**：记事本/Sakura Editor + 全文 Grep + 手工模板置换。本项目要回答的问题是：

> 能否用一套"结构感知编辑器 + 状态快照回放"，把口上作者从"写完→开游戏→玩到对应状态→肉眼验收"的循环里解放出来？

### 1.1 为什么选口上域而不是通用 ERB IDE

- **规模足够大但边界清晰**：2,285 个文件、99,028 个函数，但全部遵循 `M_KOJO_K{n}_` 命名约定与统一分发协议（`@KOJO_MESSAGE_SEND`），可校验、可导航、可建模。
- **验收痛点最尖锐**：口上是纯文本+条件分支的艺术品，同一函数在不同好感/时间/部位状态下输出完全不同，**没有状态回放就无法验收**——这是作者耗时最长的环节。
- **受众真实存在**：eraTW 活跃补丁生态（本次实测 300+ 个第三方补丁目录，其中口上补丁约 60 个）证明持续有人产出；era 系同构游戏（eraK/eraSQN/eraNAS/era命蓮寺）共享协议，后续可低成本扩展。

## 2. 目标用户画像（基于 155 角色目录实测分型）

| 作者类型 | 占比特征 | 典型产出 | 核心痛点 |
|---|---|---|---|
| **完整剧本作者** | 少数，头部（早苗 7 套、さとり 7 套、こいし 6 套） | 10~33 个 ERB 分册 + 自建 CFLAG 1000+ 段状态系统 + KOJO_OPTION 游玩指南 UI | 函数体量巨大后导航困难；CFLAG 位图自己都会记混；跨版本迁移靠 KOJO_VERSION 手写 |
| **模板置换型** | 中等（"賑やかし"系列：神子56/こころ57/芳香89…11 个角色同一模板批量产出） | K1 占位符全文置换 → 改名换色 | 置换容易漏改（`K1` 子串会误伤 `K10+`）；不知道哪些家族函数"标配四件套"没接 |
| **单文件简陋版** | 不少（era命蓮寺系列：ぬえ/村紗/星/響子 为单文件口上） | 1~2 个 ERB | 入门门槛：PRINTFORM/CALLNAME/变量语法全靠读别人代码 |
| **别人修正/汉化者** | 大量（目录里"別人修正""汉化日志"高频出现） | 在原作上打补丁 | 编码混杂（Shift-JIS/UTF-8-BOM）、找不到函数归属、改完不敢测 |

**推论**：编辑器的核心价值排序应为 ①导航与归属识别 > ②模板/脚手架 > ③条件可视化 > ④状态回放验收 > ⑤编码/写保护。回放虽是差异化卖点，但入口价值靠前三项。

## 3. 产出物形式实测（作者交付物的真实形态）

上一轮调研定案，此处为设计输入的权威事实：

### 3.1 目录与文件布局

```
ERB/口上・メッセージ関連/個人口上/
└─ {三位角色NO} {英文名} [{日文名]}/     ← 目录前缀 = CHARA CSV 的 NO 编号
   ├─ {剧本名}/                          ← 同角色 1~7 部作品并存（引擎上限 10）
   │  ├─ M_KOJO_K{n}[_{セレクタ}]_{分野}.ERB
   │  ├─ readme.txt / ライセンス.txt      ← 作者惯例随附
   │  └─ (可选) KOJO_OPTION 子系统、日记模板等
   └─ of_new_kojo_api_TEST.ERB           ← 部分角色带 API 演示文件
```

- **不是单文件**：典型作品 10~16 个 ERB，按分野拆分（イベント/コマンド/カウンター/性交系/奉仕系/絶頂/日記/依頼/刻印取得/弾幕勝負…）。
- 文件名 `_2/_3` 后缀 = セレクタ编号；函数名 `M_KOJO_K1_2` = 灵梦 2 号剧本。
- **同角色多套靠家族名隔离**：`M_KOJO_K{n}` 函数体内 RESULTS 三元组声明家族名（前导下划线）/显示名/悬停简介，后续函数名为 `M_KOJO{家族名}_…_K{n}`。

### 3.2 引擎侧对接协议（编辑器必须理解的"隐性契约"）

分发器 `KOJO_MESSAGE.ERB`（1,590 行）27 个主 CASE，统一三段式骨架，对编辑器的关键含义：

- **函数存在即接通**：TRYCALLFORM 按命名模板匹配，**写错函数名=静默失效**（无报错）→ 编辑器的"家族完整性检查"是刚需；
- **标配四件套**：FLAGSETTING(196)/COLOR(190)/ENCOUNTER(192)/EXTRASOURCE(189) 各约 190 个 ⇒ 约 190 个口上家族全量接入，**缺 FLAGSETTING 每次读档出警告**——可自动校验；
- **MESSAGECHECK 位协议**（bit0 跳共通文/bit1 跳口上）、门禁矩阵（口球/时停/眠姦/扮演，且各 CASE 宽严不一）、TCVAR:50 射精部位 16 位表——条件抽取要按此建模；
- **K1 模板置换发行**：官方模板以 K1 为占位编写，作者复制后全文替换 `K1→K{No}`。注意 `K1` 是 `K10`~`K199` 的子串，**手工置换有误伤风险**，这是脚手架功能的直接依据；
- 口上可自占 CFLAG 1000+ 段、可发指令改数值、可带 KOJO_OPTION 子系统——**口上是"半个插件系统"**，编辑器不能按纯文本编辑器建模。

### 3.3 作者教程现状（游戏自带文档分析）

- 《口上作者様へ》：官方对接说明，核心指导是"**想找全部触发时机就 Grep KOJO_MESSAGE_SEND**"——直接印证导航工具缺位；
- 《超初心者向け口上の書き方入門》：全文只教 PRINTL/PRINTFORML/CALLNAME/SETCOLOR 四件事；
- Sakura Editor 用 `.khp` 关键词帮助文件（CSV_ABL/CSV_CFLAG…11 个）：社区唯一"IDE 功能"，本质是静态变量字典；
- 《変数一覧》13 个 txt：手工维护的变量表——我们的 variableSchema 可以直接吃这些数据并覆盖。

## 4. 竞品与替代方案

| 方案 | 形态 | 与本项目差距 |
|---|---|---|
| VS Code + EraBasic 高亮插件 | 社区事实标准 | 仅语法高亮；无函数家族导航、无协议校验、无状态预览 |
| Sakura Editor + .khp | eraTW 官方推荐 | 变量提示，无任何结构理解 |
| Pyera 口上制作工坊 | 可视化积木 | 产出 `.py`，服务自有 Pera 框架，不进 ERB 生态 |
| EraElectron `.kojo` (YAML) | 新格式口上 | 仅 UmaERA 引擎；反向印证"专用中间格式"路线在 era 社区推不动——**作者要的是直接编辑 ERB** |
| KojoDown (Markdown 口上规范) | 规范文档 | 无工具落地，已停更 |

**结论**：① 不发明新格式，直接编辑 ERB 是唯一可行路线；② "结构感知 + 状态回放"在 Emuera 生态无先例，属空白。

## 5. 技术可行性（基于已完成的技术资产盘点）

本项目不是从零起步，以下资产已验证可行：

| 资产 | 位置 | 对编辑器的价值 |
|---|---|---|
| 口上机制全解（15/16 篇文档） | `reverse-engineering/eratw4.980-口上机制深挖.md` 等 | eratw-adapter 的全部领域知识：27 CASE 路由表、门禁矩阵、CFLAG 位图、多剧本系统 |
| 存档解析器 | `reverse-engineering/sav-parse/parse_sav.cjs`，6 个真实 sav 全字节零残余 | 快照回放第一来源（fromSav）直接移植；7-bit 字节前缀/MASTERNAME 条件保存等协议已定案 |
| CliDebug 驱动 | `_clidbg_test.cjs` + 引擎 `CliDebugHost.cs`（JSON Lines 协议） | 活会话变量读取（fromCliDebug），编辑保存→游戏内即时验证的通道 |
| 主循环/词法源码精读 | `eratw4.980-引擎源码分析.md`、`-词法与表达式.md` 等 | ERB 解析器的语法基准：宏展开 bug、字符串 7-bit、LazyLoading 排除规则（含 #FUNCTION 的文件整文件排除）等已知陷阱 |
| 口上金样本 | eratw4.980 本体 2,285 文件 | 解析器 golden test 数据源（fixtures 取脱敏结构子集） |
| FORM 三连符号映射 | `===`→CALLNAME:PLAYER 等 | 预览渲染的插值规则，含"ERB 禁用三连符号做分隔线"的告警规则 |

### 5.1 关键技术判断

1. **解析器做"结构感知"而非完整解释器**：函数边界、PRINT 变体、IF/CASE 嵌套、变量引用、条件谓词抽取——不执行赋值/调用链。风险可控，金样本充足。
2. **状态回放是近似求值**：条件在快照上求值，输出三档置信度（确定命中/疑似/无法判定）；深链路（CALL 链、RAND 分支）落到 CliDebug 实测兜底。**不承诺与游戏逐字一致**，UI 必须明示。
3. **编码是脏活但已摸清**：Shift-JIS/UTF-8-BOM 混杂 + 引擎侧 DetectEncoding 有已知 bug（Process.cs:589）→ 编辑器统一探测+归一化，是"汉化者"画像的刚需。
4. **写保护**：游戏目录整体只读，唯一可写路径显式声明 + 自动备份 + 原子写。eraTW 补丁生态惯例是整目录覆盖安装（大量"■バックアップ必須■.txt"），我们据此把备份做成一级特性。

## 6. 痛点 → 功能映射总表

| # | 痛点（实测依据） | 对应功能 | 优先级 |
|---|---|---|---|

| P3 | K1 模板置换漏改/误伤 | 脚手架：AST 级全文置换（只换函数名 token）+ 生成后完整性报告 | v0.3 |

## 7. 风险与开放问题

| 风险 | 等级 | 对策 |
|---|---|---|
| 受众规模小（eraTW 活跃口上作者约数十人量级） | 中 | 定位为"先解决自己的问题"的工具；架构上多游戏接口保证沉没成本可控 |
| eraTW 版本更新致 schema 漂移（本次实测 4.980，社区版本 4.9xx 并行） | 中 | variableSchema 版本化 + 加载时校验 + 提示重建索引 |
| 近似回放误判导致作者不信任 | 高（信任类） | 三档置信度显式标注 + 一键跳 CliDebug 实测；不夸大宣传 |
| 版权/内容敏感（口上含 R18 文本） | 中 | fixtures 只留结构样本；工具本体不内置任何剧本内容；发布渠道规避 |
| 范围蔓延成通用 era IDE | 中 | ARCHITECTURE.md §1.2 非目标条款硬约束 |
| 引擎方言（各 era 游戏 M_KOJO 前缀不同：紅魔館 @KOJO→命蓮寺 @M_KOJO 等） | 低 | 全部收敛进 game adapter 的 conventions |

**待决策**（与 ARCHITECTURE.md §10 合并追踪）：桌面壳 Tauri vs Electron；Monaco 内嵌 vs companion 模式；角色号映射动态解析 vs 静态表。

## 8. 结论

1. **立项依据成立**：产出物形式明确（目录 + `M_KOJO_K{n}_*` ERB 集）、协议集中可建模（单一分发器 + 命名约定）、痛点真实（Grep 式工作流 + 无法离线验收）、且我们已持有全部关键技术资产（sav 协议/CliDebug/领域文档）。
2. **建议切入顺序**：先做导航+校验（P1/P2/P5，纯静态、零风险、立刻自用），再做脚手架（P3），最后上快照回放（P4，差异化核心）。与 ARCHITECTURE.md 的 v0.1→v1.1 路线一致。
3. **唯一战略约束**：一切游戏知识进 adapter 插件，内核零游戏名——多游戏扩展是本项目区别于"又一个高亮编辑器"的结构性赌注。
