# 升糖重做的依据：全量语料实测 + 不变量分层 + 方案

- 日期：2026-10-12
- 状态：**测量已完成，结论已定；代码未动**。本文是后续动工的判断依据。
- 起因：`docs/LIFT-REPOSITION-2026-10-12.md` §2 提出「换 tree-sitter 重做预筛」，理由是
  「现有 erb-parser 的手写扫描器预筛过度严格」。本文对这个前提做了量化核验，
  **结论是前提不成立**——解析器不是瓶颈，瓶颈在它下游的三个具体缺陷和一个用错了的判据。
- 关联：本文不推翻 LIFT-REPOSITION 的第一点（升糖只用于看、零写盘），只推翻它的第二点
  （换 tree-sitter），并给出替代方案。

---

## 〇、先看结论

1. **解析器几乎是完美的**：全语料 93,410 条升糖拒绝记录里，因为「ERB 解析不出来」而拒绝的
   只有 **5 条**。配合 `BASELINES.md` §4 的 187/493,712 谓词未解析（0.04%），
   手写扫描器对真实语料的解析准确率是 **99.96%**。
2. **升糖确实几乎不工作**：2,285 个文件里只有 914 个（40.0%）产出过任何候选；
   全语料只产出 22,496 个候选，覆盖 64,689 行，占「有糖形态的 PRINT 行」的 **6.5%**。
   块级候选更是少到几乎没有：`if-block` 3,239 个（**每个文件平均 1.4 个**）、
   `selectcase` 266 个（**每 8.6 个文件才有 1 个**）。
3. **头号成因是一行簿记代码**：`lift.ts:549` 的 `skipBlock` 在记录拒绝之后，会把整个被拒区间
   标记为「已消费」，导致行级扫描（`lift.ts:1090`）直接跳过这些行。
   **一个块被拒，块内所有台词行一起陪葬。** 临时注掉这一行做对照实验：
   有候选的文件 40.0% → **76.2%**，候选数 22,496 → **714,384（×31.8）**，
   行覆盖率 6.5% → **75.7%**。
4. **第二成因是「全有或全无」的块级自证**：块体内只要有一行注释或空行，整个块（含所有嵌套层）
   被拒。语料里注释+空行占全部行的 **26.8%**，所以一个 20 行的块能过自证的概率是 **0.19%**，
   30 行是 **0.0085%**。嵌套越深块越长，被拒越必然。
5. **`tree-sitter` 不是杠杆**：它要替换的是一个只失败 5 次的解析器。而且本机构建链前提
   **一个都没装**（tree-sitter CLI / emscripten / docker / clang / gcc 全无，Rust 只有 msvc target）。
6. **真正需要重新定义的是判据**：现在把「逐字节 round-trip 自证」用在了「显示」上。
   这个判据是为「写回作者文件」设计的，用在纯显示上属于**过严到让功能失效**。
   本文 §六 给出三层不变量的划分。

## 二、语料长什么样（这决定了什么方案可行）

全量 2,285 个 `.ERB`，**3,599,696 行**。

| 类别 | 行数 | 占比 |
|---|---|---|
| **注释行**（`;` 开头） | **847,125** | **23.5%** |
| 空行 | 118,820 | 3.3% |
| 注释 + 空行合计 | **965,945** | **26.8%** |
| PRINT 家族行 | 1,073,307 | 29.8% |
| 其中**有糖形态**（`PRINTFORMW/L/DW/DL`） | **999,114** | 占 PRINT 的 **93.1%** |

**第一个要紧的事实：注释占了将近四分之一的行。** 这不是零星现象，是这份语料的书写风格——
作者用 `;-----------------` / `;小分岐` / `;通常帰宅` 这类分节线组织长文件，
用 `;CFLAG:1:1005  昏睡红茶事件` 这类行给变量编号写含义。任何"整块内不许有注释"的判据，
在这份语料上等于"整块一律拒绝"。

**第二个要紧的事实：台词行的语言覆盖率其实很高。** PRINT 变体全分布：

```
PRINTFORML=362370  PRINTFORMW=331508  PRINTFORMDW=160998  PRINTFORMDL=144238   ← 这四个有糖形态，合计 999,114
PRINTL=23086  PRINTW=16840  PRINTDW=14532  PRINTDL=7236                          ← 非 FORM 系，糖恒产 PRINTFORM*，无对应写法
PRINTFORM=5997  PRINTFORMD=1754                                                  ← FORM 但无 W/L 后缀（不换行不等待），规范 §3.3 划为能力边界
PRINTDATA=906  PRINTDATAW=956  PRINTDATAL=1060  PRINTDATADL=298  PRINTDATADW=198  PRINTDATAD=24   ← 数据表系，v1 刻意不做
PRINT=743  PRINTD=214  PRINTBUTTON=264  PRINTLC=39  PRINTFORMLC=11  PRINTPLAINFORM=9
PRINTS=8  PRINTPLAIN=8  PRINTSW=2  PRINTSL=2  PRINTV=2  PRINTFORMKW=2  PRINTFORMC=1  PRINTFORMK=1
```

也就是说：**语法糖的关键字覆盖不是瓶颈**。93.1% 的 PRINT 行语言上都能表达，
但实际只升出了 6.5%。中间那 86.6 个百分点全部损耗在识别策略上。

真正的语言缺口只有三处，都是有意的：
- 非 FORM 系 PRINT（61,694 行，5.7%）——糖恒产出 `PRINTFORM*`，没有对应写法；
- `PRINTFORM` / `PRINTFORMD`（7,751 行）——不换行不等待，规范 §3.3 明确划为能力边界；
- PRINTDATA 系（3,442 行）、循环、TRY 系、`SIF`、标签/`GOTO`——v1 刻意不做。

### 3.2 拒绝记录的成因分布

先澄清一个容易误读的口径：**93,410 不是错误数，也不是解析失败数。**
它是升糖建议器按契约要求「显式、不静默」记录的**每一处"我不建议这里升糖，理由是 X"**，
每条带 `fromLine / toLine / reason / message`，UI 面板显示为「未建议区间」。
它是诊断日志的条数。跨 2,285 个文件，平均每个文件 41 条。

| 成因 | 条数 | 占比 | 其中含注释/空行 | 实际是什么 |
|---|---|---|---|---|
| `mixed-domain-line` | 30,030 | 32.2% | 28,156（**93.8%**） | 块体内有注释/空行/不合格行 → 整块被拒 |
| `not-covered` | 27,822 | 29.8% | 25,371（91.2%） | **其中 27,694 条是别名建议**（另一个功能：「这个变量在本文件出现 N 次，值得起别名」），因变量以原生 ERB 形态出现而无法自证。区间跨整个文件（如 `24-10809`） |
| `transpile-error` | 17,121 | 18.3% | **18（0.1%）** | **纯生成器缺陷**：lift 产出的糖引用了未声明的标识符 |
| `unsupported-print-variant` | 9,722 | 10.4% | — | 该 PRINT 变体没有糖形态；**部分消息是错的**（见 §4.5） |
| `roundtrip-mismatch` | 5,569 | 6.0% | 40 | 生成的糖能编译，但产物与原文对不上（多为嵌套块递归组装不精确） |
| `unsupported-control-flow` | 2,692 | 2.9% | 1,985 | 块内有 `SIF` / 循环 / TRY 系 / PRINTDATA 系 |
| `label-or-goto` | 443 | 0.5% | 280 | 含 `$标签` 或 `GOTO` |
| `macro-or-directive` | 6 | ~0 | 5 | 含 `#` 预处理或 `@` 函数声明 |
| **`unparsable-condition`** | **5** | **0.005%** | 4 | ← **只有这 5 条是解析器的账** |

区间宽度分桶：`w=1`（单行）12,389 / `w=2-20` 33,590 / `w=21-100` 19,521 / `w>100` 27,910。

**归因口径的自我修正**：最初我按「区间内是否含注释/空行」统计，得到 59.8%。
但 `not-covered` 里的别名建议区间跨整个文件（`w>100` 有 27,910 条），这种区间必然含注释，
归因失真。剔除后只看 ≤100 行的窄区间：65,500 条中 28,763 条含注释/空行 = **43.9%**。

**还要再诚实一层**：43.9% 仍是**相关性不是因果**。一个 141 行的块里出现一行注释是大概率事件，
它可能其实是因为别的原因被拒的。要拿到因果结论，唯一办法是让 codegen 真的保留注释/空行、
再跑一次探针看 `mixed-domain-line` 掉多少。这个实验没做（本轮不动代码）。

## 四、五个具体缺陷（带文件行号与真实样本）

### 4.1 `skipBlock` 的「已消费」传播 —— 头号成因

`packages/plugins/kojo-sugar/src/lift.ts:539-550`：

```ts
/** 记录一次块级跳过，并**同时**把该区间标记为已消费 */
function skipBlock(skipped, consumed, fromLine, toLine, reason, message): void {
  skipped.push({ fromLine, toLine, reason, message });
  markConsumed(consumed, fromLine, toLine);   // ← 这一行
}
```

而 `liftPrintLines`（`lift.ts:1090`）的第一句是：

```ts
if (consumed.has(lineNo)) continue;
```

**后果**：一个 IF 块因为体内有一行注释而被拒 → 整个块（可能上百行）被标记已消费 →
块内所有 `PRINTFORMDL 台词` 行连看都不看就被跳过。这正是 LIFT-REPOSITION §2.1 描述的
「块内出现注释或空行就整块跳过并标记已消费，导致真实口上文件大量 PRINT 行无法被行级扫描单独提升」
——**该文档这一段诊断是准确的**，只是它把成因归给了"手写扫描器预筛"，归错了对象。

**对照实验**（临时注掉 `markConsumed` 那一行，跑完已 `git checkout` 还原）：

| 指标 | 改前 | 改后 | 变化 |
|---|---|---|---|
| 有候选的文件 | 914/2285 = 40.0% | **1742/2285 = 76.2%** | +36.2pp |
| 候选总数 | 22,496 | **714,384** | **×31.8** |
| `print-message` | 18,991 | **710,879** | ×37.4 |
| `if-block` | 3,239 | 3,239 | **不变** |
| `selectcase` | 266 | 266 | **不变** |
| 覆盖行数 | 64,689 | **756,577** | ×11.7 |
| 行覆盖率 | 6.5% | **75.7%** | +69.2pp |
| 显式拒绝记录 | 93,410 | **422,565** | ×4.5 |

改后拒绝记录成因：`unsupported-print-variant` 233,922 / `roundtrip-mismatch` 74,042 /
`transpile-error` 48,367 / `not-covered` 33,058 / `mixed-domain-line` 30,030（不变）/
`unsupported-control-flow` 2,692（不变）/ `label-or-goto` 443 / `macro-or-directive` 6 /
`unparsable-condition` 5。

**怎么读这张表**：

- `if-block` / `selectcase` **完全没变**，因为这个改动只解锁行级提升；成功候选的互斥标记
  （`lift.ts:630` 的 `markConsumed`）没有动。语义上这是对的：
  **成功的候选之间仍然互斥，失败的块不再霸占行号。**
- 拒绝记录从 93,410 涨到 422,565 **不是质量下降**。改前升糖器只「看过」约 11.6 万个区间，
  剩下约 95 万行 PRINT 它根本没去看；改后它看了约 113 万处。
  拒绝数暴涨是因为**终于开始检查那些行了**，每检查一处就如实记一条结论。
  93,410 这个数偏小恰恰是 bug 的症状：不是拒绝得少，是没走到判断那一步。
- 但这带来一个**必须同时解决的副作用**：面板的「未建议区间」会被 42 万条淹死，
  而且会与候选区间重叠自相矛盾（同一段既"已建议"又"未建议"）。
  只改一行就交付，等于把一个识别问题换成一个噪声问题。见 §七。

### 4.2 块级自证是「全有或全无」，且递归放大

`lift.ts:994-1042` 的 `renderSugarBody` 是块体组装器。它的失败模式是**任何一行不合格就整体 `return null`**：

```ts
if (content.length === 0) return null;      // lift.ts:1006  空行打断连段（保守）
if (content.startsWith(';')) return null;   // lift.ts:1007  注释行（保守：糖片段里保留会破坏比对）
...
if (closeIdx < 0 || all[closeIdx]!.line > toLine) return null;   // :1015 嵌套块没有完全落在区间内
if (sub === null) return null;                                    // :1020 递归子块失败 → 父块失败
if (sugar === null) return null;                                  // :1030 PRINT 变体无糖形态
if (hasInlineCondition(content)) return null;                     // :1037 含 \@…\@
```

`return null` 往上传播到 `buildIfSugar`（`:687`）→ `tryLiftIf`（`:590`）→ `skipBlock(..., 'mixed-domain-line', ...)`。

**嵌套本身是支持的**（`:1010-1023` 会递归处理体内的 IF / SELECTCASE），
但递归是链式的：**最内层的一行注释，会逐层 `return null` 干掉整个外层块。**

配上 §二 的 26.8% 注释+空行密度，一个块能被升糖的概率约为 `0.732^N`：

| 块长 N 行 | 整块内无注释无空行的概率 |
|---|---|
| 5 | 21.0% |
| 10 | 4.4% |
| 20 | **0.19%** |
| 30 | **0.0085%** |

**所以「嵌套几层就不能升糖」是数学必然，不是运气差。** 实测抓到的真实样本：

```
M_KOJO_K1_2_functions.ERB:29-33   第 29–33 行的块体无法构成一致的糖节点（文本域与逻辑域混行）
  原文: IF RM_RESOURCECHECK(リソース名)
        CALL PRINT_IMAGE(リソース名)
        ;ELSEIF SHOW_BOTE(NO:TARGET)          ← 就是这行被注释掉的 ELSEIF 杀死了整块
        ;	CALL PRINT_IMAGE(@"ボテ_{NO:TARGET}")
        ENDIF

M_KOJO_K1_2_イベント.ERB:257-398  第 257–398 行的块体无法构成一致的糖节点   ← 141 行，概率上为 0
  原文: IF GETBIT(CFLAG:31,0) || GETBIT(CFLAG:31,1)
        PRINTFORML 「――哈欠…………哦？你是谁？参拜客？」
        PRINTFORML 「虽说神社并不小、但也不会是迷路的程度吧、赛钱箱可不在这里哦？」
        PRINTFORMDL 灵梦一边打了个哈欠一边伸着懒腰打了个招呼
        ...
```

### 4.3 `transpile-error` 17,121 条：lift 忘了生成「别名」声明

这一桶的注释污染只有 18 条（0.1%），**跟注释空行完全无关，是纯粹的生成器缺陷**。真实样本：

```
M_KOJO_K1_2_functions.ERB:13-17
  消息: 生成的糖片段未通过转译（未定义的标识符「TARGET」——若它是自定义变量名或角色引用，
        请先在文件头用「别名」声明。）
  原文: IF CHECK_NUDE(TARGET)
          服装 = 裸
        ELSE
          服装 = 服
        ENDIF

M_KOJO_K1_2_functions.ERB:19-21
  消息: …未定义的标识符「服装」…
  原文: IF RESULT:1
          服装 += RESULTS
        ENDIF

M_KOJO_K1_2_functions.ERB:25-27
  消息: …未定义的标识符「INDEX」…
  原文: IF INDEX >= 1
          リソース名 = %リソース名%_{INDEX}
        ENDIF
```

成因很清楚：lift 把原生 ERB 的条件表达式直接塞进糖的块头（`如果 CHECK_NUDE(TARGET)：`），
但糖的转译器要求表达式里的标识符必须先在文件头用「别名」声明过。
**lift 没有为这些标识符生成别名声明**，于是自己生成的糖自己编译不过。

`TARGET` 是引擎内置的角色指针、`RESULT` 是内置返回值——这些本该是糖的保留代词或内建标识符，
却报「未定义」。这说明**转译器的标识符解析与引擎关键字字典之间有缺口**，值得单独查。

改前 17,121 条 / 改后 48,367 条，是第三大桶，且**修它不需要动任何规范**。

### 4.4 `comment-interference` 这个跳过码全量发出 0 次

### 4.5 `unsupported-print-variant` 的消息是错的

## 五、为什么 `tree-sitter` 不是杠杆

### 5.1 数据上的理由

- 因解析失败而拒绝的：**5 / 93,410 = 0.005%**；
- `BASELINES.md` §4：493,712 个谓词里未解析 **187 = 0.04%**；
- `macro-or-directive`（LIFT-REPOSITION §2.1 提到的「`@` 函数边界深度栈不重置」可能造成的后果）
  全量只有 **6 条**。

换掉一个准确率 99.96% 的解析器，去解决一个占 0.005% 的问题，收益与代价不成比例。
而 §四 列的五个缺陷，**没有一个**是解析能力问题。

### 5.2 环境上的理由（本机 2026-10-12 实测）

`tree-sitter build --wasm` 的两条路前提**一个都不在**：

| 工具 | 状态 |
|---|---|
| `tree-sitter` CLI | 未安装 |
| emscripten（`emcc` / `emsdk`） | 未安装（`~/emsdk`、`C:\emsdk`、`C:\tools\emsdk` 均不存在） |
| docker | 未安装 |
| clang / LLVM | 未安装 |
| gcc / `cl.exe`（MSVC 命令行） | 不在 PATH |
| Rust | 已装 1.99.0，但 `rustup target list --installed` **只有 `x86_64-pc-windows-msvc`**，无 `wasm32-*` |
| wasm-pack / wasm-opt / wasmtime | 未安装 |
| Node / pnpm / npm | 24.19.0 / 11.22.0 / 11.17.0，registry = npmmirror（直连可用） |

要走这条路，先得装 emsdk（约 1GB，下载源在本机网络环境下可能被墙）或 docker。
这会给一个目前**零原生构建依赖**的仓库加上工具链负担（贡献者门槛 + CI 复杂度）。

### 5.3 唯一可能成立的动机（未测量，不替用户否掉）

当前扫描器是一次性全文件扫描，**没有增量重解析**。在 Monaco 里改一个字就要重扫整个万行文件，
这个成本本轮没有测量。如果将来要做「边打字边折叠、边升糖」的实时体验，
**增量解析才是 tree-sitter 的真正卖点，跟命中率无关**。

若这个动机成立，工具链代价才值得付。但它需要单独立项、单独测量，
不应该挂在"升糖识别失效"这个已经被证伪的理由下面。

## 六、真正的问题：判据用错了层

### 6.1 先澄清现在的 round-trip 是在证什么

容易误读的地方：这里的逐字节比对**不是**「中文源码 ↔ 原版源码双向可逆」。

正向（`.kojo` → `.ERB`）从来没有做过 round-trip，它的验证是 golden
（产物逐字节等于规范 §6.1/§6.2 的期望产物）。这一层没有问题，也不该动。

`lift.ts` 做的是**反向识别的自证**：

```
原生 ERB 片段 → 猜一个等价糖片段 → 用既有转译器编译回 ERB → 与原文逐字节比
```

它证明的是「**我猜对了这段 ERB 的意思**」。因为编译是多对一的
（多种糖写法可以编译出同一段 ERB，而手写 ERB 可能根本不是任何糖写法的产物），
逆向识别本质上是猜测；「编译回去能一字不差还原原文」是一个便宜的、可执行的猜测正确性判据。

设计意图记录在 `lift.ts:7-22`：「本模块的应对不是把启发式调准，而是**让误报在结构上不可能发生**」。
这个意图在**要写回作者文件**的年代是完全正确的——改错一个字节就是事故。

### 6.2 但定位已经翻转，判据没跟着翻转

`LIFT-REPOSITION-2026-10-12.md` §1.1 已经把升糖定位改成「**只用于看，零写盘**」，
`.ERB` 现在是恒只读的。

**纯显示的话，对不上不损失任何东西**——最坏是预览略有偏差，
而折叠展开就能同时看到糖写法与原文（这个 UI 已经在 `3466df7` 里做好了）。
用一个为"写盘安全"设计的强判据去卡"显示"，结果就是 §三 的数字：块级候选每文件 1.4 个。

### 6.3 「语义等价」在这里是不可执行的判据

有一种意见认为：语法糖的黄金法则是「不改变 AST/语义」，应该验证语义等价而不是字节可逆，
具体做法是「准备一组 EraBasic 测试脚本，原版和糖版各跑一遍，比较输出、变量、错误码」。

**这个方向对，但本项目执行不了。** 原因：

- ARCHITECTURE §5.5 的结论是「**让引擎保持黑盒**，工具只做状态传送门」；
  §5.6 的受管引擎（把 Emuera 作为常驻子进程接入）明确「**默认不立项**」，
  要满足三个触发条件之一才启动。
- Emuera ERB 是图灵完备的，语义等价不可判定。没有解释器，就没有「跑一遍比输出」这条路。

所以可行的替代品是三件事，都不需要引擎：

1. **映射规则集封闭且逐条可审计**——规则表小，每条单独写单测，
   正确性由构造保证（`IF X` → `如果 X：` 是 1:1 语法映射，不需要"证明"），而不是由比对保证；
2. **匹配不上一律原样保留原生 ERB**（fail-visible）——符合项目铁律「不静默」；
3. **落盘路径额外加归一化 token 比对**——只在真的要写 `.kojo` 时启用，不用于显示。

### 6.4 一处需要修正的说法：这个糖不是「关键字替换」

上述意见的推理框架建立在「只做关键字替换，其余原样保留」上，
并据此建议「非关键字部分字节不变」的自检。

**本项目的糖是重构式的，不是替换式的**：

- 台词行**整个丢掉** `PRINTFORMDL` 前缀；
- 缩进块**不写** `ENDIF`（由缩进语义取代，产物里再由 codegen 补回）；
- `%CALLNAME:MASTER%` 可以变成别名/插值形态。

所以「非关键字部分字节不变」在构造上**不可能成立**——关键字之外的东西也变了。
对重构式糖，能承诺的最强不变量是：
**归一化后的 token 序列等价 + trivia（注释/空行）一一对应 + 行号可映射**。
空白与结构可以重排，注释和语义不能丢。

### 6.5 三层不变量（本文的核心建议）

| 层 | 用途 | 不变量 | 验证方式 | 现状 |
|---|---|---|---|---|
| **A** | `.kojo` → `.ERB` 编译 | 产物逐字节等于规范期望产物 | 既有 golden（规范 §6.1/§6.2 行号锚定） | ✅ 已交付，**不动** |
| **B** | ERB → 糖**显示**（零写盘） | 每条映射规则单独语义保持；**不做整段自证** | 封闭规则表逐条单测 + 不匹配则原样保留 | ❌ 需重构（现在错用了 A 层判据） |
| **C** | ERB → `.kojo` **落盘转换**（§1.3 分支1） | 归一化 token 等价 + **注释/空行完整保留** + 行号可映射 | 编译回 ERB 后比对归一化 token 序列；不等价 → 该段退回原生直通，**绝不静默丢弃** | ❌ 前置是改规范 §3.10 |

**关键认识：这三层是不同的问题，不能共用一个判据。**
现在的 bug 就是把 A 层的判据（逐字节）套用到了 B 层（显示），于是 B 层几乎不工作。

而 C 层的前置——让糖的 AST 能装下注释和空行——恰恰也是 §4.2 那个「注释杀死整块」的根治办法。
两条路在这里汇合。

### 6.6 C 层要动什么（现在做不到，原因很具体）

规范 v1.2 §3.10 明文规定（原文照录）：

> **注释**：`;` 起至行尾（与 ERB 一致，可写行内注释）；编辑器显示为灰色
> **空行**：仅用于分隔，**不影响产物**

实现忠实执行了它：

- `packages/plugins/kojo-sugar/src/lexer.ts:126-127, 163-164`：确实产出了 `blank` 和 `comment` 两种 token；
- `packages/plugins/kojo-sugar/src/parser.ts:503-508`：
  ```ts
  case 'comment':
    this.cursor.next();
    return null;          // ← 消费掉，然后丢弃
  case 'blank':
    this.cursor.next();
    return null;          // ← 同样丢弃
  ```
  （`:1033` 处块体内也是同样处理）
- `packages/plugin-api/src/sugar.ts` 的 `SugarNode` 联合有 15 个节点型
  （`textLine` / `heartLine` / `ifBlock` / `ifExpr` / `whenBlock` / `whenExpr` / `randomBlock` /
  `randomInline` / `choiceBlock` / `colorBlock` / `timingBlock` / `rawLine` / `rawFunctionBlock` /
  `aliasDecl` / `interpolation`）——**没有 comment，没有 blank**；
- 所以 `codegen.ts` 无从重现它们（它的 `blank()` 是"在生成块之间插空行"的排版工具，与源注释无关）。

要改的话，涉及面：契约新增节点型 → parser 保留 → codegen 输出 → **golden 全部重锚**
（`kojo-sugar/tests/goldens/` 逐字节等于规范原文，规范一改期望产物就变）→
已编译产物字节变化（对已有 `.kojo` 用户是可见变更）。

**风险点**：产物里多出注释行，对 Emuera 是无害的（`;` 注释是惰性的）；
但多出**空行**需要单独确认——规范 §3.3 曾专门规避「空假分支 + `W` 会产生空行 + 无用等待」，
那是指 `PRINTFORMW` 空文本会在游戏里显示一个空行并等待，与"源文件里的空行"是两回事，
不要混淆，但改动时必须分别验证。

**较低风险的折中**：只保留**注释**（`;` 在 ERB 里确定惰性），空行仍然丢弃。
这能解掉 §4.2 里绝大部分「注释杀死整块」的情形，而 blast radius 小得多。
是否够用需要实测（做法：临时让 codegen 输出注释，重跑探针看 `mixed-domain-line` 掉多少）。

## 七、建议的方案

### 7.1 B 层：从「整块自证」换成「逐行局部映射 + 单行降级」

映射规则表（封闭、可逐条单测）：

| 原生 ERB | 糖显示 | 依据 |
|---|---|---|
| `PRINTFORMW 「台词」` | `「台词」` | 已有能力 |
| `PRINTFORMDL 旁白文本` | `旁白文本` | 已有能力 |
| `PRINTFORML` / `PRINTFORMDW` | 同上（`续` 标记按 §5.1 逆算法） | 已有能力 |
| `IF <条件>` | `如果 <条件>：` + 体缩进一级 | **纯局部**：`scanControlFlow` 已提供 kind / expression / **depth** / line，缩进直接查 depth，不需要递归、不需要整块校验 |
| `ELSEIF <条件>` | `否则如果 <条件>：` | 同上 |
| `ELSE` | `否则：` | 同上 |
| `ENDIF` | *(缩进结束，不显示)* | 同上 |
| `SELECTCASE <主体>` | `当 <主体>：` | 同上 |
| `CASE <值>` | `是 <值>：` | 同上 |
| `ENDSELECT` | *(缩进结束)* | 同上 |
| `;注释` / 空行 | **原样透传**（`;` 注释在糖里语法完全一样，规范 §3.10 承认它） | 无需任何转换 |
| `SIF` / 循环 / TRY 系 / PRINTDATA / `$标签` / `GOTO` / 非 FORM PRINT / 含 `\@…\@` 的行 | **原样保留为 ERB**（就是用户期待的"少部分原代码"） | fail-visible，不猜 |

**这个方案的关键性质**：

1. **天生不怕嵌套**——每行独立判定，缩进查 depth 表；一行失败只影响那一行，不往上传播。
   这直接解掉 §4.2 的链式 `return null`。
2. **不需要动冻结规范**——因为它不产出 `.ERB`，只产出显示。B 层与 C 层解耦。
3. **顺带消灭 42 万条拒绝噪声**——不再有"候选列表"这个概念，只有一个整文件开关，
   以及「这些行保留了原生写法」的说明。§4.1 的副作用自动消失。
4. **与 §1.1「`.ERB` 恒只读」天然一致**——它是投影，不是可编辑文本。

**UX 变化**：从「💡 逐条候选 + 右侧面板列表」变成「**整文件一个开关：显示为糖**」。
这更贴近用户描述的「随便打开一个 ERB，一键被识别，前端显示成语法糖，少部分留原代码」。
已建的 ViewZone 折叠机制可以复用（折叠区间从"每个候选"变成"每个连续的可映射段"），
展开时仍然是糖在上、原文在下。

**代价**：失去「误报在结构上不可能发生」这个强保证。
缓解办法是把保证换成另一个形式——**规则集封闭 + 每条规则单测 + 不匹配一律原样保留**。
实践上这比现状更强：现状的失败模式是"什么都识别不出来"（用户体验为废物功能），
新方案的失败模式是"这一行保持原生写法"（用户看得见，且不会误导）。

**需要单独确认的风险**：一行看起来像 PRINT，但其实处在字符串续行、PRINTDATA 数据表体、
或 `@` 原生函数块内部时，不能误映射。判据必须来自 `scanControlFlow` 的 depth 与上下文，
不能只看行首正则。这一条要写进单测。

### 7.2 与 §4.1 那行改动的关系

§4.1 的 `consumed` 修复（1 行）能立刻把行覆盖率从 6.5% 拉到 75.7%，
但它是在**保留现有架构**的前提下的止血；§7.1 是把架构换掉。

两者不冲突，但**如果决定走 §7.1，就不必单独做 §4.1**——因为 §7.1 里根本没有
"块被拒就吃掉整段"这个机制了。反过来说，如果 §7.1 要排期，
§4.1 可以作为先行止血（代价是必须同时处理 42 万条拒绝的呈现，见下）。

### 7.3 C 层（落盘转换）的前置与顺序

C 层是 `LIFT-REPOSITION §1.3 分支1`（检测到用户要编辑 ERB → 自动转 `.kojo`）的硬前置。
只要想让 `.ERB` 有编辑出口，C 层就绕不过去。

顺序建议：
1. 先做 §6.6 的**低风险折中实验**（只让 codegen 保留注释，不动空行），
   重跑探针，量出 `mixed-domain-line` 实际掉多少——**这一步是把 §三 的相关性变成因果**；
2. 依据实测结果决定是否动空行、是否重锚 golden；
3. 再写 ERB → `.kojo` 转换器：能映射的映射成糖，映射不了的走 `.kojo` 已有的
   **原生直通**（`rawLine` / `@` 原生函数块），保证零内容丢失；
4. 落盘前做归一化 token 比对，不等价则该段退回原生直通。

注意 `LIFT-REPOSITION` 已经点出的坑：**糖写在 `@` 原生块内不会被编译**，
所以转换后的 `.kojo` 要真正可用，时机体内的可升糖片段必须还原成真正的 `时机` 块糖语法，
不能整函数塞进一个 `@` 块了事。

## 八、未决问题（需要拍板）

1. **块级糖对你重要吗？**
   如果主要想要「台词行看起来像糖」，B 层（§7.1）就够了，C 层可以无限期推迟。
   如果想让 `.ERB` 有编辑出口（自动转 `.kojo`），C 层是硬前置。

2. **注释在你的口上工作流里是什么地位？**
   23.5% 的行是注释。它们是纯给自己看的分节标记，还是承载了某种约定（比如工具会读的元信息）？
   这决定「产物丢注释」是可接受的构建产物行为（像 minify），还是不可接受的信息损失。

3. **42 万条拒绝记录怎么呈现？**（只在做 §4.1 止血时需要回答）
   倾向：按成因聚合成计数、点开才展开，且**落在候选区间内的拒绝不再单独列出**。
   更好的口径可能是改文案——不叫「未建议区间 N 条」，
   而叫「已检查 N 处，建议 M 处，不建议 K 处（点开看原因）」。
   那样这个数字对作者是信息而不是警报。
   若直接走 §7.1，这个问题自动消失。

4. **UI 那条路径为什么一个候选都没显示？**
   实测有 914 个文件、22,496 个候选，但用户反馈「从没见过一次升糖」。
   这两件事不该同时成立。可能原因：💡 / ViewZone 触发条件太窄
   （要光标正好停在可升糖片段上，且 adapter 提供分野模板）、UI 接线未通、
   或者打开的文件正好落在 60% 零候选那一堆。
   **这一条本轮未查。如果 22,496 个候选在界面上一个都出不来，
   那不管上面怎么重新设计都是白搭——这可能才是「从没见过」的直接原因。**

- 开词就是块型，六个变体全测到：`PRINTDATAL 1,077｜PRINTDATA 999｜PRINTDATAW 956｜
  PRINTDATADL 298｜PRINTDATADW 198｜PRINTDATAD 24`（合计 3,552 块）。
