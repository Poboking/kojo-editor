## 一、核心主张

口上编辑器里的语法糖，本质不是"给代码换皮"，而是一层**面向剧本的 DSL**。它让作者写的是"带条件的对话稿"，而不是程序。这条主张决定了所有后续设计判断。

铁律是**双向可逆编译**：

- **降级**：糖一键生成 100% 合规的原生 ERB，丢进 個人口上 文件夹就能被 Emuera/eraTW 加载。
- **升糖**：社区已有的老 ERB 能反向导入为剧本视图。

这条铁律是工具能否被社区接受的分水岭——做不到，就是又一个自嗨引擎。

---

## 二、必要性：原生 ERB 对口上作者是灾难

口上作者群体是"会写文的"和"会写代码的"两拨人，社区现状是工具几乎只有语法高亮（Notepad++ 的 `eracode.xml`、VS Code 的 erabasic 插件，后者作者自己承认"与其叫编辑器不如叫高亮工具"）。

新人卡壳点高度一致：

- 编码必须手动另存为 UTF-8
- 口上加载不出来、满屏乱码
- 函数重名报错
- CFLAG 越界

ERB 本身还有一堆反直觉的坑：

- 命令/变量/运算符必须半角，命令后必须跟半角空格
- `PRINTFORM` 忘了 `FORM` 就把 `%CALLNAME%` 原样打印
- `IF`/`ENDIF` 靠人工配对，极易漏
- `RAND:3==0/1/2` 连写导致概率不均
- 死分支无法自查

**结论**：语法糖的必要性 = 把"编程"降级成"写稿 + 勾条件"，让文笔好的人零代码产出口上。

---

## 三、受众分析

口上作者不是程序员。这决定了：

### 中文关键字是主路径

英文关键字对他们是额外认知负担，而 EraBasic 已有的英文关键字（`IF`、`PRINT`）是他们被迫忍受的东西。中文关键字让代码读起来像剧本。

### Kotlin/C# 的结构思想值得迁移，但以中文形态呈现

有价值的是**结构**——字符串插值、`when` 表达式、命名参数、扩展属性、范围/集合字面量——不是英文词汇。把这些结构用中文表达，既保留美感又消除语言障碍。

### 英文关键字作为隐藏别名存在

允许输入 `if`、`when`、`say` 并自动识别，服务于有编程背景或从 ERB 迁移来的作者。但默认补全只显示中文，避免新手困惑。

### 中文关键字的设计标准是"读出来像人话"

如果某个译名读起来别扭，说明它不该出现。lambda、closure 这类口上作者不需要接触的概念，直接不暴露。

## 四、设计原则

1. **糖要"薄"**。不是设计新语言，而是把 EraBasic 最别扭的写法包装成自然直觉。每个糖有明确的一对一转译规则，转译结果可读、可调试。
2. **优先级由口上场景驱动**。高频操作是"输出文本 + 按条件分支 + 插入变量 + 随机选择"，语法糖优先覆盖这四类。
3. **不要为"省几行代码"而设计，只为"消除认知负担"而设计**。判断标准：如果作者需要查文档才能写出某段代码，那段代码就值得有语法糖。

## 五、具体语法设计

### 1. 对白行——消灭 PRINT 前缀

独立成行的文本即对白，行尾轻标记控制换行/等待：

```
「%TARGET%，今天也来训练了?」      ← 独立行，默认 PRINTFORMW
「嗯……」 ⏎                        ← 带续行符，编译成 PRINTFORML
```

→ `PRINTFORMW 「%CALLNAME:TARGET%，今天也来训练了?」`

### 2. 插值——统一 `{}` + 芯片渲染

原生三套记号（`%STR%`、`{NUM}`、`\@ c ? a # b \@`）统一成 `{}`：

```
{TARGET}          → %CALLNAME:TARGET%
{好感度}          → {CFLAG:TARGET:好感度}
{恋慕 ? "…只有你" : "别靠太近"}
                  → \@ TALENT:TARGET:恋慕 ? … # … \@
```

编辑器识别语义，在剧本视图渲染成彩色胶囊。

### 3. 中文条件块——缩进即配对

```
当 好感度 ≥ 1000 且 恋慕:
    「只有你，我不讨厌。」
否则当 思慕:
    「别靠太近。」
否则:
    「……」
```

→ `IF ... ELSEIF ... ELSE ... ENDIF`，编辑器自动补齐 `ENDIF`。

### 4. 等概率随机组——修掉 RAND 的坑

```
随机:
  - 「嗯。」
  - 「哦?」
  - 「……」
```

→ 编译成 `LOCAL = RAND:3` 后 `SELECTCASE LOCAL`（而非连写 `RAND`），保证概率严格均等。

### 5. 语义化旗标——CFLAG 1000~1999 起名字

```
旗标 已告白 = CFLAG:TARGET:1037
```

编辑器维护映射表并编译回数字。

### 6. 演出指令

```
@立绘 笑顔 服1     → CALL PRINT_FACE, 60, "笑顔", "服1"
@色 #ff8080        → SETCOLOR 0xff8080
```

### 7. 文件头 front-matter

把口上开头的样板（`#FUNCTION`、`#DIM`、`VER` 检查、函数名前缀防重名）收进顶部声明区，一键生成合规骨架，并强制作者前缀（如 `K60EN_`）避免函数重名冲突。

### 8. 其他候选（来自 Kotlin/C# 讨论）

- 命名参数：`按钮(文本: "打招呼", 返回: 1, 条件: 好感度 >= 30)`
- 扩展属性：`她的好感度 += 5`，编辑器映射到 `CFLAG:TARGET:5`
- 集合字面量：`random ["她笑了笑。", "她叹了口气。"]`
- 安全调用：`她的昵称 ?: "无名"`

## 六、混合与边界

语法糖和原始 ERB 可以同时存在。关键不是"没有难点"，而是用显式边界把难点隔离。

**核心机制**：ERB 块用显式标记包裹（如 ` ```erb ... ``` `），转译器将其视为不透明节点，内部完全不解析，原样输出到最终 ERB 的对应位置。糖区域才走词法/语法分析。

实现要点：

- AST 统一管理糖节点和 RawBlock 节点，生成代码时按顺序拼接
- 糖生成的标签加唯一前缀（如 `__sugar_1`），避免与手写 ERB 冲突
- 维护源映射（生成行 → 源文件位置），支持错误回溯
- 编辑器功能上，糖区域和 ERB 区域用不同的高亮和补全

---

## 七、现代编辑器的边界识别方案

不让用户手写丑陋的显式边界，是现代编辑器的趋势：

| 方案 | 适用场景 | 特点 |
| --- | --- | --- |
| TextMate 注入 | VS Code 扩展 | 正则驱动，开发成本最低，但嵌套/歧义时失效 |
| Tree-sitter 注入 | 独立编辑器 | 增量 LR 解析，精确识别 AST，支持递归注入和错误恢复 |
| LSP 注入 | JetBrains 等 | 最完整的编辑体验，但实现最重 |

最优雅的方案是 **Tree-sitter + 语法驱动的自动注入**：为糖语法和 ERB 分别编写 grammar，通过 `injections.scm` 自动切换。但"优雅"不等于"当下最优"——从简化子集开始，逐步迭代。

**分层策略**：默认自动识别 + 显式边界兜底 + 预览面板显示转译结果。

## 八、导入与升糖策略

编译是有损的。语法糖和手写 ERB 编译后可能产生完全相同输出，一旦失去源文件，就无法区分。**这不是技术难点，是信息论意义上的不可能。**

**解决方案：源文件才是权威。**

- **源格式（混合格式）**：唯一可编辑对象，糖节点和 RawBlock 在 AST 层面天然区分
- **编译格式（.erb）**：构建产物，供引擎加载，不承担可编辑职责

旧 ERB 导入**不建议全自动升糖**。原因：

- **逆向不唯一**：`PRINTFORMW 你好，%NAME:TARGET%。` 可能来自糖，也可能手写
- **上下文敏感**：同一 IF 块在不同上下文中对应不同糖写法
- **风险不对称**：误升糖不易察觉，后续 bug 难追踪
- **社区 ERB 多样性**：历史遗留写法、个人风格、移植代码大量存在

正确做法是**"建议式提升"**：导入旧 ERB 作为纯 RawBlock 源文件，编辑器后台分析，对可识别模式给出升糖建议，逐条确认，且以"编译结果逐字节一致"为安全前提。

**更轻量的中间态**：只做语法高亮、补全、别名提示，不做结构转换。作者看到的还是原始 ERB，但能获得编辑器帮助。

## 九、美观与阅读性

口上是剧本，就该像剧本一样呈现。**双视图 + 实时预览**：

- **剧本视图**：对白用可读比例字体，条件块是可折叠卡片，人名是彩色芯片，随机组是并排卡片，视觉噪音全部隐藏
- **源码视图**：等宽字体的糖代码，给懂行的人微调，两视图实时双向同步
- **右侧 Emuera 黑底预览**：勾选角色状态，即时看到这条口上在该条件下实际会显示什么——不用反复重启游戏 debug。**这是杀手级功能**
- **语义配色**：对白暖色、人名胶囊、数值等宽强调、条件关键字冷色、注释灰
- **危险波浪线**：死分支、全角字符、RAND 不等概率、缺 ENDIF、CFLAG 越界、函数重名、缺末尾换行，实时标红并进侧栏问题面板

---

## 十、实用性红线

1. **产出即合规 ERB**，不改变社区"丢 .erb 进文件夹"的分发方式
2. **渐进采用**：糖与原生 ERB 可混写，老口上可导入升糖
3. **编码自动化**：保存强制 UTF-8(-BOM)、强制末尾换行、全角空格自动检测
4. **兼容现有宏库**：TW 的 VS Code snippets 可作为糖的"片段库"导入

---

## 十一、设计哲学

**"文本优先、结构可视、双向可逆"**——作者面对的是剧本和条件卡片，编辑器在背后替他们对抗 ERB 的半角陷阱、配对地狱和概率坑。

一句话：**代码的形态趋近于它所描述的事物本身。** 口上作者写出来的应该是剧本，而不是程序。
