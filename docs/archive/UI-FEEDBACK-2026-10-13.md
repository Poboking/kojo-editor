## 二、第 4 项：糖视图改为「虚拟文档」的提案（**待用户拍板，勿在补测批里顺手做**）

**方向**：不再用 ViewZone 贴糖文本，而是给一份只读的**虚拟 model**（非 `file:` URI，专用 languageId），
内容 = 糖文本；原文行紧随其后并按 ADR-0006 默认收起。这样原生拿到字号、字体、折行、缩进、光标与滚动，
对齐问题从"要修的症状"变成"不存在"。

**必须付的三笔代价**（都在代码里可指认）：

1. **行号坐标系换了**。`editor.revealLocation` 现在把行号当真实行用（`App.tsx:96` → `ProjectView.tsx:309` →
   `EditorPane.applyReveal:323-333`），波浪线、状态栏行数、跳转全部要经映射。
   现契约 `SugarProjectSegment` 只到**段粒度**，承载不了行级映射（ADR-0006 §后果 同一条），
   ⇒ 需要 **additive** 字段（如 `lineMap: {sugarLine: number; sourceLine: number | null}[]`），**这是糖组的实现面**。
2. **保存链必须拒绝虚拟文档**。`pickSaveHandler`（`EditorPane.tsx:63-80`）按路径 `matches()`，
   `.erb` 结尾的虚拟路径会被 `.kojo` 保存接管者或内核缺省 `writeText` 认下来 ⇒ 一旦写盘就是**改坏游戏文件**。
   落点是给虚拟文档独立 scheme（如 `sugar-view:<真实路径>`），宿主在保存 / 脏标记 / 标签标题三处分支。
3. **同一 model 只能一个 languageId**。原文行若按糖语法着色会错（大写指令 / `%…%` 在糖语法里不是那个意思）。
   可行解：新增一个双态 Monarch（行首匹配「全大写指令 / `#` / `@` / `$`」进 ERB 态，否则进糖态），
   复用 `kojo-language.ts` 的词表单一真源；不新建第三套词表。

**建议的最小顺序**：先落第 5 项（现方案下的折叠柄 + 已收起行数可见，纯宿主、无契约），
再做第 4 项（要契约，须糖组实现 `lineMap`）。两者合流后，"展开原文"就是取消 `setHiddenAreas`，不需要第二套机制。

**要用户回答的三个问题**：
- (a) 原文行是否也写进虚拟文档？（写了才能靠隐藏/显示实现展开；副作用是 Ctrl+F 会搜到拼接文本）
- (b) 是否同意给 `SugarProjectSegment` 加 additive 行级映射（糖组实现、宿主消费）？
- (c) 状态栏/行列显示哪套行号？建议：显示行号为主 + 悬停给「原文第 N 行」。

## 三、第 6 项的定性路径（**已结案**，判据口径写给下一位）

真实壳里要区分三种失败，修法完全不同——本项先前就在第 ② ③ 条上判错了对象：

- **接线失效**：点击后菜单项根本没执行（抛异常 / 事件没绑）⇒ 修宿主。**本项不是这种**。
- **有落点、没有落脚点**：菜单把草稿指向某个作用域（这里是 `projectDir`），但那个作用域
  **没有渲染行内框的槽位** ⇒ 点击只是往 state 写了个 draft。⇒ 修的是**渲染槽位**，不是 handler。
  这就是用户看到的"点了没生效"。
- **建完了看不见**：东西真写到盘上了，但那一层只渲染登记过的条目（项目行只列 `workspace.json` 里的包）
  ⇒ 盘上有、面上无，用户读来仍然是"没生效"。⇒ **只修上一条等于修了一半**。

⇒ 口径：**「菜单有这一项」必须同时问两句——"点了有没有地方输入"、"建完有没有地方看见"**。
⇒ 探针不能只看 `.context-menu` 有没有出现，要一路量到 `.kp-draft-input` 出现 → Enter →
  **盘上存在该目录** → **树里出现那一行**，四段都在才算过（§5.107 那 16 项）。

## 四、第 7 项：ERB 结构错误波浪线（**已落地 §5.109；第二步 💡 一键补齐已落地 §5.112**；规格原文留着给下一个改判据的人）

**精度原则**（沿用本项目一贯口径：错标比不标危险，宁少勿错）：只报**可证明**的结构错误——

1. 孤儿闭合语句（`ENDIF` / `REND` / `ENDSELECT` / `ENDCATCH` / `ENDFUNC` … 找不到对应开块）；
2. 文件/函数结束仍有未闭合开块（指到开块行）；
3. 分支语句出现在其所属开块之外（`ELSE` 不在 `IF` 链里、`CASE` 不在 `SELECTCASE` 里）。

**不报**：未知变量名、未知函数名、`CALLFORM` 悬空引用——这些要么需要全库语义、要么引擎本身宽容，
报出来就是误报农场。**配对表一律复用 `erb-parser/scanner.ts` 的 `OPEN/BRANCH/CLOSE/TRY_*` 现有表**，
不在别处再抄一份（两处表必然漂移，这是本项目写过的教训）。

**落点**：结构判定作为 `erb-parser` 的纯函数（表在它手里），经 `ErbParserService` additive 暴露；
波浪线由 `ui.editor.decorator` 通道进宿主 `refreshMarkers` ⇒ **宿主零改动**即见效。
`.kojo` 侧已有糖语法诊断（23 码闭集 + 判定面板），本项只补 ERB。

> **落地时的两条更正**（§5.109 实测，别再按下面原文的假设办事）：
> ① "函数边界"**不能用 `@` 前缀判**——语料里大量跨行 `CALL` 的续行以 `@"…"` 开头，第一版就这样在真实语料里误报 23 条
>    （一次误报连环两条：未闭合 + 孤儿闭合）；判据收成形如"函数名首字符是字母/下划线"。② 大文件**不需要**降级：最大单文件（52,602 行）
>    体检 23.4ms / 28.5ms，与既有骨架扫描同量级；引入"某些文件不报"等于制造第二种真相。封顶 50 条是另一回事（防问题列表被淹）。

> **第二步（§5.112）**：波浪线之后，💡 直接把缺的闭合语句补在**配对器给出的那一行之前**（可撤销、不碰磁盘）。
> 只有 `unclosed-open` 有动作——多写的闭合词也可能是我们把函数边界漏判了，删行不做。门槛两条：路径必须可写、
> 光标必须落在波浪线那一行（不确定就不给）。实机半边：清单 §六 7.D 由 §5.113 的 50 项探针覆盖（含轴一 7.21）。

**性能门槛**（不是猜测，要有实测）：波浪线走既有 `MARKER_DEBOUNCE_MS = 250` 去抖；
超大文件按既有降级口径处理，并给出**真实耗时读数**，不允许"输入即卡"。
