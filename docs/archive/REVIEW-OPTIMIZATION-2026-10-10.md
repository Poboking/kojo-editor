工程纪律是本项目最强项——"不静默、不猜测、一切未知带原因"贯彻到字节层；解耦审计、金样本回归、先测量再定语义都做得很扎实。方案层面存在若干会在 v1.x / v2 阶段反咬的债务与盲区，共 13 项，分四组。其中 **1 项为真实文档矛盾（ARCH §6 vs ADR-0002 vs 实现）**，其余为前瞻性风险提示。

## 1. 语法糖的定位（结合最新决策）

用户明确：**语法糖是必要的**——ERB 语言本身对口上作者是负担，降低写口上门槛是项目核心目标之一；**但双视图（源码↔剧本双向可逆）可有可无**。据此修订原审阅第 10 条：

- 保留语法糖作为主线方向，不挪出 v0/v1。
- 放松"双向可逆编译"的硬承诺（语法糖设计稿 §八 自己也承认"信息论意义上的不可能"）。
- 建议 MVP 先做**降糖只读预览**（ERB→剧本视图，零写风险）验证需求，升糖 / 双向同步作为可选后续，不阻塞主线。

→ 原"语法糖分心、移出主线"的判断作废；改判为"必要方向，但抓手先收窄到只读预览"。

## 3. 优化点清单

### A. 架构边界

**A1. `state-replay` 服务键与 ADR-0002 自相矛盾 —— ✅ 属实（唯一硬文档 bug）**

- **证据**：`ARCHITECTURE.md` §6 L579 写 `requires: ['game.adapter','snapshot.source']`；但实现 `packages/plugins/state-replay/src/index.ts` L34-40 的 `requires` 为 `Project/Slots/IO/SnapshotSource/ConditionExtractor`（**无** `game.adapter`）；取适配器走 L49-58 的 `slots.query('game.adapter')` + `project.adapterId`，与 family-index 同款模式。`ADR-0002` L17 明确"服务键 `game.adapter` 不由适配器插件强制提供"。
- **结论**：ARCH §6 那行错，HANDOFF §四 对。纯文档债，无代码影响。
- **建议**：① 改 ARCH §6 为正确 `requires`；② 补 ADR-0002 修订，写明"强类型适配器引用通过 `slots.query('game.adapter', adapterId)` 获取"。低成本高价值。

**A2. 解耦审计只查 import 越界，查不出逻辑泄漏 —— ✅ 属实**

- **证据**：`tools/audit-decoupling.mjs` L84-101 为文本 / 词汇级检查（内核扫 `GAME_WORDS` 黑名单，插件查禁 import kernel / 禁插件互 import），无法识别"插件内硬编码 eraTW 专属常量"类语义泄漏。
- **建议**：加"伪 adapter 冒烟"——造返回空 / 随机数据的假 adapter 跑通 onboarding + 索引 + 回放链路，确保真正的多游戏隔离，避免 v2 接入才暴露返工。

**A3. 预览职责两处说法未对齐 —— ✅ 属实**

- **证据**：语法糖设计稿 L211"右侧 Emuera 黑底预览…杀手级功能"；`ARCHITECTURE.md` §5.4 L185-189 `preview.renderer` 输入正是回放 `evaluatePreview` 产出的 `PreviewLines[]`。二者是同一条链路（状态→筛选行→渲染），并非两个独立能力。
- **建议**：v1.0 收口明确分工——回放面板负责"状态→分支 / 文本预览"，糖预览（若做）复用 `preview.renderer`，不要自建渲染逻辑。

### B. 性能与规模

**B4. 索引 / 抽取在主线程，Worker 化未落实 —— ⚠️ 部分属实（数字被混淆）**

- **证据**：`HANDOFF.md` L88 索引本身 ~2.9s（99,104 函数 ✓）；L94 条件抽取全量 ~6.2s、冷启动 ~13s。即"13s"是**条件抽取冷启动**，非索引耗时。`ADR-0003` L32 仅说"若 v0.2 卡顿移入 Worker"，目前未做。
- **建议**：onboarding 显示进度条；erb-parser + condition-extractor 的构建搬进 Web Worker（内核无平台依赖，天然可搬）。表述修正：是"抽取链冷启动 13s"，不是"索引 13s"。

**B5. dirty 检查每击键 O(n) —— ✅ 属实**

- **证据**：`packages/app/src/ui/EditorPane.tsx` L108-110 为 `ed.getValue() !== originalRef.current` 全量比较，无版本号优化。
- **建议**：改用 model 版本号 / 脏标记位，一行级改动。

**B6. state-view 默认保留全部 cells —— ✅ 属实**

- **证据**：`packages/plugins/state-replay/src/state-view.ts` L78-118 构造时一次性遍历建档；"16k 变量"有出处（`HANDOFF.md` L86：16,005 变量 / 档）。面板已按（档×角色）惰性重建。
- **建议**：首次 `createView` 解析整档仍可能内存峰值，建议 Worker + 流式解析大档。

### C. 可靠性与数据正确性

**C7. M3 写保护纵深防御没做 —— ✅ 属实**

- **证据**：`CODE-REVIEW-2026-10-10.md` L68-70 已认定 Rust `write_file_bytes / remove_file / rename_path` 接受任意绝对路径，白名单只在 JS 层；`HANDOFF.md` L357"遗留 M1 / M3 随 v0.3 排入"→ 确认未做。
- **建议**：**M3 排进 v0.3 并优先于 v1.1 注入器**——注入器本身是写路径，M3 不做会让 v1.1 的"写测试档"在无第二道闸下开放写。

**C8. Int64 精度是 v1.1 的真·地基 —— ✅ 属实**

- **证据**：`HANDOFF.md` L92 RANDDATA SFMT 625 ≈2.8e16，save01+ 写回显式拒绝，方案 B = `rawBytes?` 原样复制未修改变量 + 被修变量含大数拒绝注入。
- **建议**：v1.1 第一步做"变量原始字节区间定位 + 金样本含修改回归"，再碰注入 UI。字节区间定位不做，注入器是半成品。

**C9. "默认场景全 0"被当确定事实 —— ✅ 属实（工程层面确有该倾向）**

- **证据**：`packages/plugins/ui-state-replay/src/index.ts` L221"重置输入为默认场景值：int=0 / str=''"；空值才按 unknown（L307、L440）。即**预填的 0 被当作已提供值参与判定**，未改时并不必然等于引擎真实默认——正是假命中风险。
- **建议**：UI 把"默认场景 / 预填 0"明确标注为"假设 / 默认值"，不伪装成确定命中。"全 0 是否恒为引擎事实"属领域语义，需逆向证据或作者确认（代码无法单方裁定）。

### D. 交付节奏与范围

**D10. 语法糖战略定位 —— ⚠️ 部分属实（结论合理，引证有偏差；已据用户决策修订）**

- **证据**：语法糖设计稿 L185"信息论意义上的不可能" ✓；`ARCHITECTURE.md` §1.2 非目标 + §9 L631"范围蔓延"红线 ✓。但 `RESEARCH.md` L33 价值排序（导航 > 模板 > 条件可视化 > 回放 > 编码）**无"锦上添花 / 雪中送炭"措辞，也未把语法糖列入排序**。
- **修订（见第 1 节）**：语法糖为必要方向，双视图可选；MVP 先做降糖只读预览。原"移出主线"判断作废。

**D11. 先 v1.0 收口再上 v1.1 —— ✅ 属实**

- **证据**：`HANDOFF.md` L357 下一批即"v1.0 收口 vs v1.1 注入器"二选一；当前 unknown 32.0%、call-context 858（L87），§6.11 已列消解路径（场景预设 / 默认值、UI 上下文增强）。
- **建议**：v1.0 先把 unknown 压到 ~20% 以下（作者敢信回放），再上 v1.1 注入器——否则加速的是还不信任的回路。

**D12. ARCHITECTURE 变 changelog —— ⚠️ 部分属实（行数被夸大）**

- **证据**：§5.8–§5.18 标题确为"…实施记录"；但实测 §5.8@264、§6@564，即该段约 **300 行**；全文 645 行。"600+ 行"是错的（≈全文总量）。"实施记录占近半"仍成立。
- **建议**：把 §5.8–§5.18 实施记录拆到 `docs/IMPLEMENTATION-LOG.md` 或并入 HANDOFF，让 ARCHITECTURE 回归设计决策本质。

**D13. 缺契约版本化 ADR —— ✅ 属实**

- **证据**：`docs/adr/` 现有 4 条（0001 工具链 / 0002 game.adapter / 0003 壳 / 0004 snapshot.source），无破坏性变更管理 / 兼容矩阵类 ADR；`ARCHITECTURE.md` §6 L570 写明 plugin-api"版本化 semver"。
- **建议**：补 ADR 约定"契约破坏性变更如何版本化 + 插件兼容矩阵"，v2 多 adapter 时防踩。
