## 二、六条建议逐条判定

1. **「`HEART_ARGS_RE` 应允许单引号 / 混合引号」→ 有害，不做。**
   引擎词法里 `@` 只有紧跟 `"` 才成为格式串，否则退化成孤立 `SymbolWord('@')`（`LexicalAnalyzer.cs:1005-1018`）；
   `'…'` 串只在 `AllowSingleQuotationStr`（HTML_PRINT）与 `AnalyzePrintV`（PRINTV 系）两个 flag 下才被识别，
   其余场景直接 `UnexpectedCharacter`（`:931 / :940 / :979-984`）。CALL 实参走 `StrEndWith.DoubleQuotation`（`:958`）。
   语料实测 0 行。**放宽 = 投影出引擎无法加载的行**，撞本项目"错标比不标危险"的红线。

2. **「应支持 `\"` 转义」→ 引擎层面为真，但收益 4 行，且审阅漏掉了语义。**
   `ReadString` 的 `case '\\'` 分支（`:528-543`；官方版 `:500-514`）读掉 `\` 后按字符分派，
   `default` 原样追加下一个字符——所以 `\"` **不闭合字符串**，且**反斜杠被丢弃**：`@"abc\"def"` 的值是 `abc"def`。
   即：真要支持，正确做法是"按引擎语义剥掉 `\`"，而不是"把字符类放宽"；照审阅字面实现会显示出一个引擎不打印的反斜杠。
   另注：`""` 双写**不是**转义（ReadString 在第一个 `"` 就 return）。

3. **「括号式尾部注释 / 多余空格会让 `slice(0, -1)` 出错」→ 无此缺陷。**
   现网是 `args.trimEnd().endsWith(')')` 后再切，尾部空白已被 `trimEnd` 吃掉；
   语料里 HPH_PRINT 行含 `;` 行中注释的只有 **1 行**，且它本就落进"形态不整齐 → 整行不动"的 fail-closed 分支。
   另：审阅举例用的 `// comment` 不是 ERB 的注释语法（ERB 用 `;`，见 `SkipWhiteSpace :810-824` 与 `Analyse` 的 `case ';'` `:1034-1046`）。

4. **「模式白名单应放宽字符类，交由 `HEART_MODES` 二次校验」→ 收益 0。**
   见 §一 取值分布：放宽 `[A-Za-z]+` 一行都捞不回（空模式与制表符不是字符类问题，全角 `Ｌ` 需要的是归一化）。
   "引擎将来扩展模式字母"是臆测：`HPH_PRINT` 的取值域已从源码钉死（§三 第 1 条），四值 + 兜底，不存在待接的第五个字母。

5. **「语料守门测试里 heart 行提前 `continue` 会遮蔽其它统计」→ 不成立。**
   六把尺子的正则全部**行首锚定且互斥**：`^\s*CALL` / 状态族名左值 / `^\s*@` / `^\s*SIF` / `^\s*PRINT`
   （`packages/kernel/tests/sugar-projection.corpus.test.ts:65-88`）。`CALL` 行不可能命中其它尺子，`continue` 饿死不了任何统计；
   FORM ⊂ OUTPUT 的重叠在 `:290-297` 是**刻意双计**（无 continue）。不变量 `projected+passthrough+native === totalLines`
   读的是 `stats`（`project.ts:509-518`），与这段分类循环无关。

6. **「`readableText` 应包 try/catch，防一行坏掉整批失败」→ 前提假，加了反而伤害纪律。**
   `readableText`（`project.ts:1131`）只做静态 Map 遍历（`PRONOUN_REVERSE`）+ 两个线性正则 replace + `deps.dictionary?.()` 查表，
   没有逐行抛错路径；唯一能抛的是外部 thunk `dictionaryOf`（`index.ts:113`，`slots.query`）与 `nameAt`（`index.ts:293`，`schema.lookup`），
   那类故障对**每一行**都抛，属接线故障而非脏数据。heart 与 SIF（`:327`）/ control（`:342`）/ assign（`:471`）/ inline（`:418`）
   在"逐行不包 try/catch"上同构；单给 heart 包一层会把接线故障伪装成"这行不投影"，违"绝不静默"。
   宿主侧已按**逐文件**降级：`ui-sugar-lift/src/index.ts:100-105`。模块内该防的位置早有示范——`safeScan`（`:1341`）只包外部扫描器。

## 三、这次核验顺带钉死的两条领域事实（留给下一批）

1. **`HPH_PRINT` 的签名与取值域已从源码确定。** 它不在 `#FUNCTION` 行上，而是新版声明：
   `ERB/ステータス表示関連/COLOR.ERB:223` → `@HPH_PRINT(対象文字列, ARGS)`，`:224` `#DIMS 対象文字列`。
   固定 **2 参**，模式字母取值：`DW/dw`→`PRINTSD`、`DL/dl`→`PRINTSDL`、`W/w`→`PRINTSW`、`L/l`→`PRINTSL`，
   **其它或省略 → `PRINTS`**（`:246` 与 `:275-287`）。
   ⇒ 这**修正了 §5.68/§5.69 记的那笔欠账**（"无模式字母 59+ 行须实机测默认模式"）：默认模式已由源码证得是 `PRINTS`
   （不换行、不等待），它**不等于四个模式中的任何一个**，糖里也没有等价写法 ⇒ E 类 63 行**继续不投影现在有源码依据**，
   不再需要实机测。

2. **G 类 73 行是目前唯一"可证安全且没做"的一档。** `CALL HPH_PRINT, "「…」", "L"` 的首参是**非 `@` 普通串**，
   引擎不展开 `%…%`，其值就是字面内容逐字符；语料里这类行的文本也不含 `%` 记号。
   ⇒ 若要接：判据必须是"普通串 + 字面量内无引号 + 模式 ∈ 四值"三条同时成立，投影文本逐字符照抄。
   收益 0.11%（73 行），属可做可不做；且要先定一条口径——糖 §3.9 的「心形」是否只承诺格式串（`@`）来源。

3. **C+D 类 1,133 行（1.68%）的正解不是"更宽的正则"，而是懂 `%…%` 与 `\@…\@` 嵌套的字面量扫描器。**
   同时要决定显示口径：`%TEXTR("嗯/啊/咿")%` 在糖视图里照抄（诚实但读者不懂）还是降糖（要新增随机选择的糖写法 = 语法层决策）。
   本回执只记录缺口与量级，**不开这个口子**。
