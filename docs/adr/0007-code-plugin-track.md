# ADR-0007: 代码插件轨立项（只立项不排期）——市场 v1 只发声明式数据包

- **日期**：2026-10-16
- **状态**：**已立项，不排期**（只定"动手之前必须先有什么"，不承诺开工时间）
- **相关**：`docs/ARCHITECTURE.md` §10「插件分发」行、本批口上市场落地（注册表仓 `Poboking/kojo-market` 已上线，CI 自动发布）

## 背景

「口上市场」v1 已全量落地：GitHub 静态索引 + ZIP 内容包 + 逐文件 sha256 锚定。市场只分发三类**声明式数据包**：

| 包类 | `PackKind` | 内容形态 | 消费侧 |
|:--|:--|:--|:--|
| 口上包 | `kojo-pack` | 文本（口上正文） | 导入向导 |
| 字典包 | `dict-pack` | 名称表 | adapter 追加轮次 |
| 模板包 | `template-pack` | 脚手架素材 | 新建向导 |

落地之后的自然一问：**能不能从市场装「代码插件」**（会执行 JS 的那种）？

现状事实（决定了这个问题的答案不是"顺手做掉"）：

- 插件持有**全权** `PluginContext`：`kernel.io` / `bus` / `storage` / 槽注册全在里面；
  内核只靠写域铁律（5/6）约束写盘（仅限 `writablePaths` + 常驻可写根，绕域唯一法定通道 `exportFile`）。
- 对**插件代码本身没有沙箱、没有权限声明字段**——插件 `import` 后与宿主同进程、同运行时。
- ⇒ 从市场装第三方代码插件 = **把内核信任面整体交出去**。补一两条校验补不上这个洞，
  需要的是先决条件（见决策 3）。

## 决策

1. **代码插件轨立项。** 目标形态定死：**可分发、可装可卸可更新的第三方代码插件**——
   一条独立轨，不是市场 v1 的延伸。
2. **不排期、不进当前版本。** 市场 v1 **只发声明式数据包**：数据不过 JS 执行面
   （口上＝文本、字典＝名称表、模板＝脚手架素材），天然不携带可执行代码。
3. **开工前置三件套，缺一不可**（"立项"的全部内容就是把这份前置清单钉住）：
   - **权限模型**：清单声明能力面（写域 / 网络 / 槽位），**内核执法**；
   - **沙箱或等价隔离**：至少要有崩溃域与执行边界；
   - **签名机制**：装载接口已预留来源字段，签名在此之上补。
4. **前置未齐之前，不得为"顺手"把代码插件塞进现有市场通道。** 要动先改本 ADR 再写码——
   不得以"反正索引与 ZIP 格式兼容"为由绕行。

## 备选方案（为何不选）

| 方案 | 为何不选 |
|---|---|
| 直接开放（市场可发任意代码插件） | 等于给任意代码全权 `PluginContext`，把内核信任面整体交出去；否 |
| 仿 VSCode 扩展宿主（独立宿主进程 + 扩展 API 层） | 工程量与工具规模不匹配，Tauri 侧无现成隔离面；暂否 |
| 先做装饰性 `permissions` 字段（只声明不执法） | **假闸门比没有更坏**——用户以为有保护而实际没有，违反「绝不静默」；否 |

## 后果与验收含义

- 市场 UI / 文案**不得暗示**"插件可下载 / 可安装"——v1 能装的只有三种声明式数据包。
- `kojo-market` 的三种 `PackKind` 是**封闭集**；新增任何**可执行**种类必须先过本 ADR。
- 将来真开工时，验收口径＝**权限声明的执法测试**：越权写盘 / 越权联网必须红（"有字段"不算数）。
