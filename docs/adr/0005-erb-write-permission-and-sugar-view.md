# ADR-0005: ERB 写权限与糖视图口径（目录分野 × 显式解锁 正交模型）

- **日期**：2026-10-12
- **状态**：已接受（用户拍板）
- **相关**：`docs/KOJO_PROJECT_AND_KOJO_TREE_DISCUSSION_MINUTES.md` §2 写保护铁律 / §7 双真相源；
  IMPLEMENTATION-LOG §5.49；提交 `7012dd9`（本组）与 `3d1f8d0`（语法糖组）

## 背景

「ERB 什么时候只读」这一道闸，两条工作线**各自重做了一次**，落点在同一个
`packages/app/src/ui/EditorPane.tsx`：

| 线 | 提交 | 模型 | 判定依据 |
| :-- | :-- | :-- | :-- |
| 本组（口上项目批 P-B0） | `7012dd9` | **按目录分野** | 游戏目录 ERB 只读；工作区内 ERB 可编辑（`kernel.io.isWritable(具体文件)`） |
| 语法糖组（批 A） | `3d1f8d0` | **按显式解锁** | `ErbUnlockDialog` + 会话内解锁路径集（不落盘）；且「解锁 ERB 编辑 ⟹ 禁用糖视图」 |

两模型**不是竞争关系而是正交关系**，但当时彼此不知情：糖分支**尚未引入「工作区」概念**，
其解锁逻辑预设"ERB 都在游戏目录里"；本组分野逻辑则完全不知道有解锁这回事。
直接合并会各留一半（工作区 ERB 被弹解锁框 / 解锁后糖视图仍可用 / 或反之）。

故先定口径，两组合并时按此对齐，不再就地即兴裁决。

## 决策

两道**正交轴**，各管一件事：

### 轴一 · 目录分野：定「默认可写性」

- **工作区（作者自有区）内 ERB：恒可编辑。** 工作区是作者自己的东西，弹解锁框等于把
  写保护铁律的代价转嫁给正常操作。
- **游戏目录内 ERB：默认只读。** 那是别人的口上，误改即事故（写保护铁律）。
- 写白名单 = **常驻可写根**（工作区根，不受项目开闭周期清空）**∪ 用户批准的项目 `writablePaths`**，
  由 `kernel.io.isWritable(具体文件)` 判定。
- ⚠ **但"编辑器当前这份文件能不能打字"不走 `isWritable`**：落地时它是内联的三条件式
  `readOnly = isErbLike(path) && !inWorkspace(path) && !allowEdit`，
  在 `EditorPane.tsx` 里**各写了一遍**（切文件时的 `updateOptions` 与 `setErbEditable` 解锁/回锁各一处）。
  `isWritable` 只管**落盘那一侧**（保存路径上的拒绝 + 保存按钮的 `disabled`）。
  两者语义一致但实现分离 —— 原稿"判定唯一真源"的说法过强，已按实现校正。
  **后续如要合并成单一真源，注意别把轴二（会话内解锁）漏掉**：`isWritable` 不知道解锁态。

### 轴二 · 显式解锁：只管「游戏目录里这一份、这一次」

- 游戏目录 ERB 需要就地改时，由 `ErbUnlockDialog` 让用户显式决定破例可写。
- 解锁态**会话内有效、不落盘**。理由沿用糖组原论证：「上次解锁过就一直可写」会让
  保护形同虚设，而重启后再点一次的代价极低。
- 解锁**不改变**轴一的默认判定——它是叠加在只读区上的一次性例外，不是扩权。

### 糖视图门：与「可编辑态」互斥

沿用糖组既定的互斥规则（同一份文件不能一边被改一边被投影），由可编辑态派生：

- **工作区 ERB 恒可编辑 ⟹ 默认禁用糖视图。** 自己正在写的源码看投影没有意义，
  要写糖请直接写 `.kojo`。
- **游戏目录 ERB 默认只读 ⟹ 糖视图可用。** 这正是糖视图的主场景：
  「打开别人写的 ERB，像看剧本一样读懂它」。
- 游戏目录 ERB 一旦解锁为可写 ⟹ 该份糖视图禁用（回到互斥规则）。

## 后果

合并 `syntax-sugar` 时，`EditorPane` 侧按下述口径落地（**本 ADR 是两组的共同依据**）：

```ts
// 轴一 + 轴二：默认可写性 ∪ 一次性例外
const editable = kernel.io.isWritable(path) || unlockedThisSession(path);
// 糖视图门：与可编辑态互斥（工作区恒不可用；游戏目录解锁后不可用）
const sugarViewAvailable = !editable;
```

> **落地形态（2026-10-13 校正）**：糖视图可用门没有按上面这个布尔式实现，而是做成了
> **入参更细的纯函数** `sugarViewAllowed({ isErbLike, inWorkspace, unlocked })`
> （`packages/app/src/ui/sugar-view.ts` 的 `sugarViewAllowed`），宿主三处（自动应用 / 首次询问 / 工具条入口）
> 共用同一判据，避免三处分叉。它比上式多管一件事：**`.kojo` 本身不投影**
> （`isErbLike === false` 直接返回不可用——它就是糖源码，再投影一遍没有意义）。
> 口径与本 ADR 一致，只是把"哪些文件算数"显式进了参数而非依赖 `editable` 反推。

- **给糖组的适配项**：解锁入口（`ErbUnlockDialog` 的触发）应只在
  `!kernel.io.isWritable(path)` 时出现——工作区文件本就可写，弹框是噪声。
> ⚠ **措辞澄清**：`sugar-view.ts` 头部注释里有「ERB 恒只读」的说法，那是**升糖重定位批**
> 时期的口径，**只该理解为"游戏目录里的 ERB 默认只读"**。按本 ADR 轴一，
> **工作区里的 `.ERB` 恒可编辑**（实机已验：新建的工作区文件直接可打字、无 🔒 徽章）。
> 读到那句注释别照抄，以本 ADR 为准。

- **给本组的约束**：不得为工作区写权限另加确认层；工作区恒可写是 P-A 常驻可写根的
  既定语义，加确认等于推翻轴一。
- 双真相源提示（面板常驻条 + 部署向导文案）与本 ADR 同源：口径是
  **「工作区为权威 · 游戏目录仅部署目标」**，写侧的体现就是本 ADR 的两道正交轴。
- 本 ADR 只定口径，不含实现。**糖视图与解锁 UI 的代码归语法糖组**（分工见
  HANDOFF），本组不代做；本组负责的是轴一（已在 `7012dd9` 落地）与工作区概念的可用性。
